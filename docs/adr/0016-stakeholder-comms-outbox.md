# ADR-0016 — A Stakeholder Comms Outbox: drafts from recorded facts, never auto-sent, closure owed to the briefed

- **Status:** Accepted
- **Date:** 2026-10-27
- **Session:** 50
- **Supersedes:** nothing. **Extends:** ADR-0008 (post-commit rules spine, new
  rules `RULE-COMMS-01..04`), ADR-0006 (canonical zero-build app: no backend,
  no network call, no new runtime dependency).

## Context

An Operational Case already schedules stakeholder check-ins (`RULE-STAKE-01`,
Mendelow cadence) but stops short of the message. The leader still re-types the
same facts (rating, owner, mitigation, review date) for each key stakeholder,
and when the case closes nothing reminds them that the people they briefed are
owed the outcome. The master prompt names "stakeholder communication drafts" as
an example gap; a repository search before this session returned no rule and no
draft or outbox structure (`grep` for draft-message/outbox: 0 hits).

The market covers the drafting half. 2026 AI status-report features (Asana
Status Reporter, Atlassian Rovo, Microsoft Planner Agent) draft stakeholder
updates from live project data, and some offer audience-specific versions
[1][2][3]. Incident-management guidance adds a closure duty: if stakeholders
were told about an incident, the closure should be communicated to them too
[4]. What the sources do not describe is a record of *who was actually told
what*, a closure obligation derived from that record, and withdrawal of
approved text when the facts beneath it change. (Competitor claims here rest on
search snippets and are **[UNVERIFIED]** against hands-on trials.)

## Decision

1. **Drafts are a typed ledger, not a sender.** `commsDrafts` (Schema v32) holds
   drafts with a status machine: `draft → approved → sent`, plus `superseded`
   and `dismissed`. The app never transmits anything. "Sent" is recorded by a
   human, or inferred from a logged stakeholder touch (`RULE-COMMS-04`).
2. **Audience is Mendelow-derived.** Only manage-closely / keep-satisfied
   stakeholders and blockers/skeptics receive a status brief. Keep-informed and
   monitor stakeholders stay on the digest cadence to avoid message spam.
3. **Content is deterministic and fact-bound.** Every number, name and date in
   a draft is read from the case. A missing fact is rendered as
   `[to confirm — …]`, listed, and reduces a readiness fraction. Financial
   exposure is quoted only when a PERT estimate exists. Nothing is defaulted in
   the text.
4. **Idempotence is content-addressed.** Each draft stores the canonical
   `fingerprint` of the facts it was written from. An unchanged fingerprint is a
   no-op, including after the draft was sent or dismissed (no nagging). A changed
   fingerprint supersedes the open draft and records the reason. An approved
   draft whose facts change is superseded with "re-approval required".
5. **Human gates.** Approval of a draft with unconfirmed facts requires an
   explicit acknowledgement. Editing an approved text withdraws the approval.
   Dismissal requires a reason. A sent message cannot be approved or edited.
6. **Closed loop.** Resolving a case withdraws unsent briefs. A closure note is
   drafted only for stakeholders whose brief was actually *sent*. Reopening
   withdraws the closure note and re-briefs with current facts. A plain
   `updateCase` into a closed status follows the same path as `resolveCase`.
7. **Single entry for each fact.** Marking a brief sent writes the stakeholder's
   `lastCommsOn` and `nextCommsOn` on the case, using the existing Mendelow
   cadence offsets. A logged touch marks the matching draft sent.

## Consequences

- **Positive.** The leader sees a concrete, sourced message per key stakeholder
  each time a case changes, and a closure owed for every relationship that was
  already informed. Every drafted, superseded and sent event is audited through
  the existing `automation.propagated` path. Demo workspaces ship a populated
  outbox generated by the real rule, not hand-written text.
- **Negative / limits, stated plainly.**
  - FMEA ratings default to 5 when left blank at case creation (existing
    behaviour in `addCase`). A stored 5/5/5 is therefore indistinguishable from
    a deliberate rating, and the readiness check cannot flag it. This is a known
    limitation, recorded here and in the audit, not fixed in this change.
  - The sent-by-touch match uses the logged date (`lastCommsOn >= draft.createdOn`).
    A touch on the same day as a draft is treated as the send. This is a
    convention, not proof of delivery.
  - Status changes are material, so each status transition re-drafts for
    key stakeholders. This is intentional but can be chatty on busy cases.
  - There is no pause switch (unlike `impactAutoPropagate`). Drafts are inert
    until a human acts, so the risk is clutter, not an outgoing message.
  - Drafts are not exported to CSV. The full JSON backup includes them.
- **Architecture.** No new module boundary, runtime dependency, network call or
  backend. The engine is a pure module (`app/core/domain/comms.js`), like the
  other domain engines. Actions use the validated `ctx.api` path. The view is
  one file. Link typing adds one entity type (`comms`) and one relation
  (`communicates`) to the shared graph vocabulary.

## Rejected alternatives

- **Auto-send through an email or chat integration.** Rejected: it would add
  network egress and a credential surface, which conflicts with ADR-0006, and
  it would send text a human has not seen.
- **LLM-written drafts.** Rejected: the drafts must be explainable and must
  not invent a number. A template that quotes only recorded facts can be
  audited line by line. Model prose would need a faithfulness check that the
  repository does not have.
- **Store the message only as a case note.** Rejected: that would not give
  status, supersession, the closure rule or typed links.
