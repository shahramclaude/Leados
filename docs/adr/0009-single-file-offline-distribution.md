# ADR-0009: Ship a single-file, offline, double-clickable LeadOS distribution

## Status

Accepted — 2026-10-26, Session 42.

## Context

[ADR-0006](./0006-canonical-zero-build-app.md) selected `index.html` + `app/**` as the
canonical zero-build application. It has no runtime framework or backend, but it is still a
folder of native ES modules loaded with `<script type="module" src="./app/main.js">`. That
works over HTTP, including the dependency-free `scripts/serve.mjs`, but it does **not** work
when a leader copies only `index.html` to another computer and double-clicks it:

- Module scripts are fetched with CORS semantics. A `file://` page has an opaque (`null`)
  origin, and local files cannot send `Access-Control-Allow-Origin`, so relative `import`
  statements are blocked. MDN's module guide and CORS error documentation describe this
  directly.
- A folder of 89 `.js` files and a stylesheet is easy to break when copied by a non-engineer;
  missing one module produces a blank page.
- A browser profile's `localStorage` is origin-dependent. Some browsers allow it for local
  files, others restrict it; Web Crypto and the File System Access API vary too. A portable
  app must degrade honestly rather than pretend records are saved.
- The owner explicitly asked for one independent HTML file that can be copied to any PC and
  run locally.

## Decision

Add a build-time distribution artifact, **`LeadOS-standalone.html`**, generated by
`scripts/build-standalone.mjs`:

1. Bundle `app/main.js` and its entire import graph into one classic IIFE using `esbuild`
   (`format: 'iife'`, `bundle: true`, `minify: true`, `target: es2020`). Classic inline
   scripts are not fetched as CORS module requests, so a `file://` page can execute them.
2. Inline `app/styles.css` into a single `<style>` tag; remove the external `<link>` and
   `<script type="module" src=...>`.
3. Set `window.__LEADOS_STANDALONE__ = true` and a distinct
   `window.__LEADOS_STORAGE_KEY__ = 'leados.standalone.v1'` before the bundle. `store.js`
   honours that key so a copied file cannot silently share or overwrite a served workspace.
4. Add a `connect-src 'none'; object-src 'none'; base-uri 'none'` CSP, a build fingerprint
   meta tag and an honest portability banner.
5. Add a **Settings → Portable offline copy** card: a download link in the served app, and an
   export/import data-migration explanation in the standalone app.
6. Add `build:standalone` and `verify:standalone` npm scripts, a regression suite, and commit
   the generated HTML so the owner can copy it immediately without running any build.

`esbuild` is a direct **devDependency**. It exists only in the build script; the generated
HTML has no npm modules, no `node_modules`, no CDN, no service worker and no network calls.
The canonical development entry point remains unchanged.

## Rationale and limits

A single-file app is the strongest form of local-first portability: TiddlyWiki has shipped an
entire wiki in one HTML file for years, and `vite-plugin-singlefile` documents the same pattern
for offline tools. LeadOS does **not** try to save records back into the HTML file itself;
browser file writes are inconsistent and dangerous. Instead:

- The **application** is portable by copying one file.
- The **data** is portable by the existing explicit JSON export/import flow.
- The standalone key avoids cross-origin data collisions.
- If `localStorage` is blocked, the store already keeps an in-memory workspace and shows a
  visible warning; `main.js` now catches `window.localStorage` access that can itself throw on
  an opaque origin.
- Optional passphrase encryption may be unavailable when Web Crypto is not exposed to a local
  file. The UI says so and plain JSON exports remain unencrypted; no false confidentiality
  claim is made.

Real Chromium/Firefox/Safari behaviour for `file://` `localStorage`, Web Crypto and downloads
remains **[UNVERIFIED]** in this container. JSDOM proves boot, routing, no-fetch behaviour and
ARIA structure, not graphical rendering or browser storage policy.

## Consequences

**Benefits**

- One 1.7 MB file can be copied to a USB stick, emailed or opened on an offline PC.
- No module/CORS failure, no relative-folder breakage, no runtime install.
- The build is reproducible, fingerprinted and testable; canonical source remains modular.
- Data separation and explicit export/import preserve the no-fabrication invariant.

**Accepted costs**

- `esbuild` is a new build-time dependency (dev-only); `package-lock.json` changes.
- The generated HTML is a build artifact committed to the repository and must be regenerated
  after canonical source changes. `npm run build:standalone` and
  `npm run verify:standalone` make that explicit.
- Minified inline JavaScript is harder to inspect than the modular source; the source
  fingerprint, schema version and commit are recorded in the HTML meta tags.
- `localStorage` capacity (~5 MB) and browser-specific file-origin behaviour still apply; a
  local file is not a backup.

## Alternatives rejected

| Alternative | Reason |
|---|---|
| Tell users to run `scripts/serve.mjs` on every PC | Requires Node and a command line; violates "copy one HTML file". |
| Keep `<script type="module">` and ask users to launch Chrome with `--allow-file-access-from-files` | Insecure browser flag, poor UX, still needs the full folder. |
| Inline every module as a separate `<script type="module">` with data URLs | Fragile import rewriting and still hits module/CORS semantics. |
| Save records back into the HTML file from the browser | File System Access API is not universal and needs permission; silent loss is worse than explicit export. |
| Use Electron/Tauri/PWA packaging | Adds an installer/runtime, contradicts the zero-build browser-native architecture. |
| Ship a ZIP of the folder with a README | The owner asked for one independent HTML file; a ZIP can still be unpacked incorrectly. |
